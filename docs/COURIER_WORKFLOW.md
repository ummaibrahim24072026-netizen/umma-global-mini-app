# UMMA Cafe — предложения курьерам и подтверждение доставки

Подготовлено в черновике. Рабочее приложение не обновлено, реальные уведомления не отправлялись.

## Маршрут

Старая кнопка Закрыть использовала белый стиль cafe-back на белом фоне. Новая «← Назад к заказу» контрастная, закреплена над картой. Закрытие, Escape и общий back возвращают к прежнему экрану и фокусу. Поздний ответ маршрутизатора не меняет уже закрытую/новую карту. При недоступном Leaflet можно выйти из модального окна.

## Подбор

- Broadcast: доставка предлагает себя всем активным курьерам этого кафе. Учитываются активность Telegram-профиля, назначение courier в кафе и доступ сотрудника; чужие кафе не получают заказ.
- Nearest: сначала один ближайший к кафе по геопозиции не старше 10 минут и с точностью до 500 м. Это расстояние по координатам, не гарантированное время поездки. Без подходящей геопозиции используется общая рассылка.
- Кухня/менеджер/официант/кассир могут вручную предложить заказ конкретному активному курьеру. Это предложение, не принудительное назначение. Остальные предложения при ручном выборе приостанавливаются до ответа/истечения срока.
- Предложение ближайшему действует 2 минуты, общее/ручное — 15 минут. Следующий кандидат выбирается после отказа или истечения предложения. Отказ с причиной 3–500 знаков остаётся в журнале и не отменяет заказ гостя. После принятия самостоятельного отказа в дороге нет: обратиться к менеджеру.
- Принятие блокирует строку заказа и закрывает остальные предложения: только один победитель. Повтор принятия тем же курьером возвращает результат. Неактивный или чужой курьер не может принять, даже если получил старое уведомление.
- Геопозиция запрашивается только кнопкой с разрешением устройства; автоматического скрытого слежения нет. Свежий снимок координат используется 10 минут. Профили и координаты не выдаются клиентам.

## Фото

Получение возможно только после готовности кухни и сохранения фото pickup. Подтверждение delivered требует сохранённого фото handover. Требование проверяет SQL для курьера и менеджера: пропуск через старую кнопку/API не проходит.

Файлы хранятся в приватном bucket cafe-delivery-evidence. В PostgreSQL хранятся заказ, курьер, этап, путь, SHA-256, тип, размер и время сохранения. Edge проверяет тип/размер, резервирует ключ операции, загружает файл без перезаписи и только затем подтверждает метаданные. При потере ответа загрузки проверяется SHA-256 реально сохранённого объекта. Сервер не утверждает по одному снимку достоверность физической передачи: это журнал загруженных подтверждений сотрудника.

Фотографию может открыть менеджер соответствующего кафе, суперадминистратор или назначенный курьер собственной доставки. Ссылка действует 60 секунд. Bucket private, дополнительная restrictive RLS-политика запрещает anon/authenticated операции в этом bucket даже при наличии общих permissive policies. Фронтенд не получает service_role. Камера/геопозиция требуют действий и разрешения владельца устройства.

## Уведомления и расписание

Предложения и очередь создаются в транзакции с заказом. После COMMIT Edge пытается отправить уведомления. Ошибка Telegram не отменяет созданный заказ. Очередь использует leases/SKIP LOCKED, неактивные/просроченные предложения не отправляются. При неопределённом ответе Telegram сообщение может повториться; повторное принятие не создаёт второго назначения.

Для автоматической смены кандидата без открытого приложения и повторных отправок нужен courier-dispatch-worker раз в минуту. Он защищён отдельным секретом (>=32 случайных знаков), хранение — Edge Secrets и Supabase Vault. Нельзя вводить секрет в frontend, GitHub или чат. Периодический SQL подготовлен в supabase/proposals/courier-dispatch-schedule.sql по официальной документации Supabase; pg_cron/pg_net и Vault настраиваются перед запуском после отдельного согласия владельца. Без worker расписания автоматическая смена по таймауту не считается включённой.

## Выпуск

До включения: проверить native PostgreSQL CI с двумя конкурирующими курьерами; создать приватный bucket и restrictive policy; настроить worker secret/расписание; развернуть новые shared dependencies и worker; проверить реальную загрузку тестовых фотографий/геопозицию на телефоне в изолированной среде. Эти действия в рабочей среде ещё не выполнялись. В режиме остановки записи сначала приостанавливается courier cron; bucket, фото и журнал не удаляются.

Перед включением требования фото необходимо завершить старые доставки, уже находящиеся в дороге без фото получения. Не фабриковать отсутствующие снимки задним числом. Идентичное изображение получения не принимается как новое фото вручения.
