# UMMA Work — аудит и рабочая ветка

Базовый маршрут рабочего PWA — `staff.html`. Публичное меню — `menu/`. У Telegram есть отдельные экраны в `index.html` со скриптами, часть которых также загружается в рабочем PWA. GitHub Pages развёртывает статические файлы при изменении `main`. Изменения Edge Functions выкладываются через Supabase отдельно.

## Карта рабочих интерфейсов

| Экран | Фактическая реализация | Состояние в ветке |
|---|---|---|
| Вход, приглашение, PWA | `staff.html`, `cafe-web`, `web-session.js`, манифест и Service Worker | Общая шапка и подпись роли. Прежние веб-сессии и приглашения |
| Сводка менеджера | `staff.html`, `web-operations.js`, `cafe-web` | Новая сводка по назначенному кафе. Счётчики заказов, выручка по журналу оплат и возвратов за 24 часа, закончившиеся блюда |
| Заказы, выдача и отмена | `kitchen.js`, `cafe-kitchen`, серверные операции Postgres | Добавлена история заказа для менеджера и обязательная причина отмены в рабочем PWA |
| Касса, смена, передача денег | `web-operations.js`, `kitchen.js`, `cafe-web`, `cafe-kitchen` | Кассир начинает с заказов к оплате. Поиск по номеру, подтверждение фактического поступления QR, серверное ограничение доступа к кассовым данным |
| Экран оплаты | `payment-screen.html`, `payment-screen.js`, `cafe-web` | Текущий отдельный экран с ограниченной сессией и только чтением |
| Кухня и оповещения | `kitchen.js`, `kitchen-live.js`, `cafe-kitchen` | Сетевая индикация и автоматическая попытка восстановления остатков и заказов. Сохранён существующий режим «кухня + касса» |
| Готовые порции, ревизия, партии | `ready-stock.js`, `cafe-web`, `cafe_ready_list`, `cafe_ready_plan`, планировщик Supabase | Синхронизация при смене кафе и возврате сети. Текст учитывает автоматический переход партии в наличие и ручной приём |
| Ингредиенты, закупки и журнал | `staff.html?work=stock`, `ingredients.js`, `cafe-web` | Веб-склад доступен кухне с назначением и менеджеру в рамках кафе. Расширенные складские операции есть в отдельных административных экранах |
| Сотрудники | `web-operations.js`, `cafe-web`, `staff-admin.js` в Telegram | Менеджер видит сотрудников своих кафе. Владелец управляет приглашениями и ролями |
| Официант | В веб-PWA — рабочий список заказов при назначенной роли. В Telegram — отдельный приём заказов, счета столов и добавление позиций | В веб-PWA список получил собственный заголовок. Полноценный веб-приём заказов официанта остаётся отдельной задачей |
| Курьер | `courier-desk.js`, `courier-workflow.js`, `delivery-tracking.js`, `courier-route.js`, серверные операции курьера | Общие рабочие стили. Прежняя очередь, маршрут, оплата при получении, отметки и фотографии |
| Сообщения, вызовы и рассылки | `connect-admin.js`, `cafe-connect`, `cafe-connect-translate`, `cafe-push` | Входящие восстанавливаются после возврата сети. Смена переписки закрывает форму предыдущей. Серверный перевод текста используется при недоступности локального |
| Админ-панель, каталог, локации, учёт | `index.html`, `js/admin/`, `products-admin.js`, `inventory-admin.js`, `accounting-admin.js` | Существующие входы через Telegram. Их отдельный аудит и перенос в веб-PWA остаются открыты |

## Обнаруженные проблемы

- Кассир открывал форму продажи вместо очереди оплаты. Подтверждение сразу с QR-экрана стойки обходилось без отдельной проверки намерения. Добавлены очередь и явное подтверждение получения оплаты.
- Раздел кассовых данных опирался на назначение сотрудника в локацию. Теперь `cashList` проверяет роль, право принимать оплату для кухни и официанта, активность филиала и точное соответствие запрошенной локации.
- История заказа в списке содержала только последнее событие. Менеджер может открыть отдельную хронологию с сохранёнными комментариями.
- Результаты опроса заказов могли оставлять старый список после ошибки фонового обновления без индикации. Рабочая доска показывает состояние связи.
- В планировании партий текст про обязательное подтверждение устарел. В рабочем Supabase включено задание `umma-cafe-finish-due-batches` с интервалом пять секунд, последние проверенные запуски прошли успешно.
- Старые локальные SQL-фикстуры воспроизводят исторические дефекты оплаты закрытого заказа и закрытия смены другим филиалом. Текущая рабочая функция закрытия смены уже содержит проверку отсутствующего назначения. Изолированный набор проверяет исправленные операции после загрузки предложений проекта.
- Общий каталог используется несколькими интерфейсами. Публичное меню распределяет ряд категорий и фото по SKU. В рабочем Supabase также есть цены наличия, отличные по механизму хранения от базового прайса. Веб-управление категориями, ингредиентами в карточке блюда, ценами, приоритетными фото и акциями требует согласования этой модели и отдельной сквозной проверки.

## Права и приёмка

- Владелец получает текущие функции управления доступом и сообщениями. Менеджер получает сводку и историю только по активным назначениям на роль менеджера и список сотрудников этих локаций. Менеджер не может изменять роли через протокол владельца.
- Заказы с предоплатой остаются в исходном серверном контуре оплаты и подготовки. Сохранены разрешённые без предоплаты сценарии, включая общий счёт в кафе и оплату при доставке.
- Реальные банковские перечисления, фоновая доставка уведомлений, GPS и воспроизведение речи на физических устройствах требуют операционной проверки.
- Проверки выполняются с изолированными тестовыми данными. Продукционные изменения и миграции в рабочую БД не выполнялись.

## Выпуск

Фронтенду для новой сводки нужны обновлённые `cafe-web` и `cafe-kitchen`. Ветка не требует миграции схемы. После проверок в изоляции и подтверждения владельца Edge Functions и Pages следует выпускать согласованно. Проверка выпуска включает свежую сессию и установленную PWA, загрузку версий ресурсов, роли менеджера и кассира и реальные действия сотрудников по подтверждённым заказам. Для отката используются предыдущие версии обеих Edge Functions и статического сайта.
