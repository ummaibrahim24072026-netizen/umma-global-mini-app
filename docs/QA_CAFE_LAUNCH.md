## Проверено

- Репозиторий GitHub, основной клиентский код, интерфейсы заказа/кухни/кассы/администрирования, существующий сценарий sandbox.

- RLS включён на таблицах. Привилегированные public-функции закрыты для anon/authenticated. Отсутствие политик RLS отмечено advisor как INFO; при доступе через сервер service_role это не само по себе ошибка. Проверка всех путей авторизации не завершена.
- В базе есть уникальный частичный индекс `cafe_one_open_bill_per_numbered_table`: один неоплаченный активный счёт на стол 1–6 в пределах кафе.
- `inventory_control_enabled=false`; `data_stage=temporary_test`. Это флаг состояния, а не отдельная база. Тестовых веток Supabase нет. Рабочие таблицы и финансовые данные не изменялись.
- `node scripts/verify-app.mjs`: успешно. Часть проверок статическая, часть исполняет функции навигации и кухни в VM.
- `node scripts/qa-cafe-launch.mjs`: успешно. Реальные функции маршрутизации столов/обработчик отправки заказа выполняются с заменами UI/API; запросы к базе заменены памятью.
- Новый набор проверяет все шесть столов, неоплаченный дозаказ, исключение оплаченных/закрытых/отменённых счетов, разделение кафе, 204 активных заказа на фоне 130 закрытых, пагинацию, ограничения курьера, сбой запроса, сбой оплаты после успешного создания и сохранение корзины при ошибке до создания.

## Исправлено в ветке, без публикации

1. **P1 — потеря новых заказов в списке кухни.** Старый серверный запрос выбирал самые ранние 100 заказов вместе с историей. Новый выбирает активные отдельно с пагинацией по id и добавляет последние 100 закрытых. Ограничения филиала и назначенного курьера сохранены. Серверный файл выгружен из Supabase и впервые добавлен в Git, чтобы исправление можно было проверить и развернуть отдельно.
2. **P1 — повторный заказ после сбоя подтверждения оплаты.** После подтверждённого создания и ошибки оплаты корзина очищается, кнопка повторного создания отключается, сообщение с номером созданного заказа сохраняется. Оплату следует проверять по существующему заказу.
3. **P1 — доставка с оплатой курьеру отклоняется сервером.** UI отправлял `paymentMethod=courier`, которого нет в серверном enum. Теперь отправляется cash, а немедленное подтверждение платежа не выполняется.
4. Выбранный `paymentTiming` отправляется серверу клиентом и сотрудником; раньше сервер всегда получал значение по умолчанию.
5. Обновлены версии JS для кеша Telegram. Регрессионные проверки добавлены в GitHub Actions.

Новая серверная выборка проверена с заменой PostgREST, но не развёрнута. Согласованность страниц при новых заказах/смене статусов проверяется следующим этапом на отдельной базе: разные HTTP-запросы не образуют одну транзакцию.

## Осталось / блокеры приёмки

- Авторизация Telegram Web: показан вход по QR. UMMA Mini App ещё не запущен в этой сессии.
- Нет отдельной staging-базы. Нельзя считать sandbox полноценной проверкой рабочих RPC: он хранит данные в `cafe_test_*` и использует другую логику.
- **P1:** создание и дозаказ не имеют серверного ключа идемпотентности. Блокировка двойного клика не защищает от потери ответа после commit, перезагрузки или повторного запроса. Требуются ключ операции и атомарное сохранение результата в тестовой базе, затем испытания параллельных запросов.
- **P1:** sandbox статусов проверяет роль, но не полный граф переходов; возможны возврат из закрытого состояния и пропуск готовки. Он не поддерживает рабочую систему столов/дозаказов. Тестовая оплата/статусы используют чтение и обновление отдельными запросами без CAS/транзакции; гонки ещё не воспроизведены.
- **P1:** SQL оплаты не запрещает отменённые/завершённые заказы; повторный paid в базовой функции может изменить сотрудника, подтвердившего оплату. Обёртка cash запрещает повтор paid, но не закрытый статус. Нужно проверить с изолированными SQL-фикстурами и исправить серверный контракт.
- Дозаказ в preparing/ready увеличивает общую сумму, но не переводит новые позиции в отдельный цикл приготовления. Клиентская индикация новых блюд есть; защита от выдачи заказа с ещё неготовым дозаказом не доказана.
- Нужно выполнить в staging: полный путь клиента и всех сотрудников, оплата/сдача/отмена/выдача, отказ без прав, два официанта на один стол, гонки оплаты и дозаказа, потеря ответа, обновление вкладки, уведомления без реальной рассылки.
- Нужна проверка на реальном кухонном планшете: звуковое уведомление, блокировка экрана, восстановление сети и заметность дозаказов.

## Продолжение

Авторизовать Telegram самостоятельно; осмотреть Mini App без записи в рабочие таблицы. Подготовить локальную или отдельно изолированную staging-базу с синтетическими пользователями и отключёнными Telegram-рассылками. Исправить оставшиеся серверные ошибки и выполнить интеграционные/параллельные тесты. Только после этого выпускать окончательный отчёт и отдельно запрашивать разрешение на рабочую публикацию.

Ветка не содержит автодеплоя Supabase. Изменение main, публикация GitHub Pages, изменение платежей и включение склада требуют отдельного подтверждения пользователя.
