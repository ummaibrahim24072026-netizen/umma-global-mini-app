## Дополнительная проверка доставки — 2026-10-13

В черновике исправлена обработка paymentMethod=courier для доставки: сервер принимает её как cash и оставляет платёж pending. Такой способ оплаты для самовывоза отклоняется. Назначение курьера и событие переведены в одну SQL-транзакцию с блокировкой заказа; повтор не создаёт событие и повторное уведомление. Выдача курьеру разрешена только для ready. Запрещены пропуск этапов, чужой курьер, изменение закрытой доставки и переназначение после получения. Сброс назначения очищает courier_telegram_id. Завершение требует delivered и paid.

Автоматические тесты проверяют наличные курьеру со сдачей, единственную квитанцию, предоплаченную доставку, отмену и повтор каждого этапа. SQL-предложение применено только к закрытой QA-схеме. CSS исправлен для длинного адреса, кнопок и выбора курьера на узком экране; создан воспроизводимый preview для ширины 320/390 px. Визуальная проверка preview в cloud-браузере заблокирована политикой file://; отсутствие переполнения на реальном телефоне пока не подтверждено.

На серверном Supabase в QA-схеме отдельно выполнена синтетическая доставка: ready → picked_up → delivered → paid → completed. Итог 120 000 VND, одна квитанция, кассир-курьер 20; повтор оплаты не создал вторую квитанцию. После обновления функции оплаты проверено сохранение закрытого доступа к QA-схеме для anon/authenticated/service_role. Курьерская оплата дополнительно ограничена собственным назначенным заказом после получения.

Скриншот владельца подтверждает отказ Invalid payment method до создания заказа в рабочей версии. В черновике также исправлены вводящие в заблуждение подписи «Оплата сразу» и «подтвердить оплату» при выборе курьера: отображаются оплата при получении и оформление доставки без подтверждения денег. Автоматический тест проверяет переключение обратно на наличные в кафе.

## Разделение времени и способа оплаты — 2026-10-14

После сообщения владельца устранена возможность показывать одновременно «Оплата сейчас» и «Курьеру при получении». Введены now (до передачи заказа), later (после трапезы, только в кафе), on_delivery (наличные при вручении, только доставка). Селекторы синхронизируются в обе стороны; для доставки по умолчанию выбран on_delivery. Выбор now снимает «курьеру» и запрашивает фактически полученную наличную сумму. Выбор «курьеру» устанавливает on_delivery и не подтверждает платёж.

API проверяет допустимую комбинацию, SQL атомарной операции сохраняет payment_timing вместе с заказом и ключом повтора. У старых записей поле остаётся NULL: способ оплаты задним числом не угадывается. Legacy paymentMethod=courier нормализуется в cash/on_delivery. Клиентская доставка наличными передаёт on_delivery. Проверены серверное отклонение on_delivery для самовывоза/QR, сохранение намерения в БД и pending при оформлении, переключения реальных DOM-контролов в обе стороны. Рабочая версия всё ещё не опубликована.
